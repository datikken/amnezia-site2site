# Архитектура VPN между двумя Keenetic через CGNAT

Для твоей задачи я рекомендую архитектуру VPS как координатор соединения + ICE hole punching + прямой UDP-туннель между роутерами + резервный relay через VPS.

Главная идея: VPS нужен для первоначального знакомства роутеров, обмена сетевыми параметрами и организации соединения. Если NAT позволяет, основной трафик идёт напрямую между Keenetic, без прохождения через VPS.

Если прямое соединение невозможно, используется ретрансляция через VPS.

Это позволит получить VPN между двумя роутерами даже тогда, когда оба подключены через CGNAT, с оговоркой: при некоторых типах NAT и сетевых ограничениях прямой P2P невозможен, поэтому relay должен быть полноценной частью архитектуры.

## 1. Общая архитектура

VPS — Control Plane

Signaling · STUN · TURN · авторизация · мониторинг

Keenetic A

LAN 192.168.1.0/24

VPN Agent

Keenetic B

LAN 192.168.2.0/24

VPN Agent

Основной канал: прямой UDP

При успешном установлении P2P

Резервный канал: VPS relay

Если прямой маршрут недоступен

Я бы разделил систему на два независимых уровня:

- Control Plane — управление, авторизация, обмен параметрами соединения.
- Data Plane — передача VPN-трафика между роутерами.

Так архитектура будет расширяться до десятков и сотен Keenetic без переделки базовой логики.

## 2. Какой VPN-протокол использовать

Я рекомендую не пытаться передавать IP-трафик непосредственно через WebRTC DataChannel.

Лучше разделить установление соединения и VPN-транспорт:

| Компонент | Технология | Назначение |
| --- | --- | --- |
| VPN | WireGuard | Шифрование и туннелирование IP |
| NAT traversal | ICE | Поиск прямого UDP-маршрута |
| Обнаружение NAT | STUN | Получение внешнего адреса и порта |
| Резервный транспорт | TURN / UDP relay | Передача через VPS |
| Signaling | WebSocket + HTTPS | Обмен параметрами |
| Управление | Собственный API | Авторизация и конфигурация |

Документы: [ICE RFC 8445](<https://www.rfc-editor.org/info/rfc8445/?utm_source=chatgpt.com>) и [TURN RFC 8656](<https://www.rfc-editor.org/info/rfc8656/?utm_source=chatgpt.com>).

Но есть важный инженерный нюанс: WireGuard не является ICE-агентом. Для динамического переключения между P2P и relay понадобится дополнительный транспортный слой или управление endpoint WireGuard.

### Два режима работы

Режим A — VPS Hub

Рекомендую для MVP

WireGuard Endpoint Discovery and NAT Traversal using DNS-SD | Jordan Whited

[jordanwhited.com](<https://www.jordanwhited.com/posts/wireguard-endpoint-discovery-nat-traversal/?utm_source=chatgpt.com>)

Оба Keenetic самостоятельно подключаются к WireGuard-серверу на VPS. VPS маршрутизирует пакеты между ними.

Преимущества:

- Работает за CGNAT.
- Не требует ICE.
- Не нужны входящие порты на Keenetic.
- Простая диагностика и восстановление соединения.
- Штатная поддержка WireGuard на совместимых KeeneticOS.

Режим B — Direct P2P

WebRTC Infrastructure Guide 2026: Signalling, SFU & Scaling at Enterprise Load

[rtcleague.com](<https://rtcleague.com/blogs/webrtc-infrastructure?utm_source=chatgpt.com>)

VPS согласовывает соединение, ICE проверяет UDP-кандидатов, после чего трафик идёт напрямую, если NAT позволяет.

Преимущества:

- Меньшая задержка.
- Нет постоянной нагрузки на VPS.
- Меньше расходов на трафик VPS.

Недостатки:

- Сложная реализация.
- Не все типы NAT допускают P2P.
- Нужен резервный relay.

Моя рекомендация: сделать сначала полностью рабочий режим A, затем добавить режим B как оптимизацию. Это позволит получить рабочий VPN до разработки сложного NAT traversal.

## 3. Развёртывание на VPS

Предлагаемый состав серверной части:

| Сервис | Назначение |
| --- | --- |
| WireGuard | Основной VPN-сервер |
| coturn | STUN/TURN |
| Signaling API | Обмен ICE-кандидатами |
| PostgreSQL | Устройства, ключи, настройки |
| Redis | Состояние соединений |
| Monitoring | Доступность туннелей |

На первом этапе достаточно WireGuard и небольшого API. PostgreSQL, Redis и coturn можно добавить по мере развития.

### Схема адресации

Например:

| Устройство | VPN IP | LAN |
| --- | --- | --- |
| VPS | 10.200.0.1 | — |
| Keenetic A | 10.200.0.2 | 192.168.1.0/24 |
| Keenetic B | 10.200.0.3 | 192.168.2.0/24 |

Условия:

- На обоих роутерах WireGuard работает в режиме клиента.
- Каждый клиент поддерживает исходящее соединение с VPS.
- На VPS разрешена маршрутизация между VPN-клиентами.
- В `AllowedIPs` указываются необходимые удалённые сети.
- Включается `PersistentKeepalive`, например 25 секунд.
- На Keenetic добавляются маршруты в удалённые LAN через WireGuard.

Официальная инструкция Keenetic: [Настройка WireGuard между двумя Keenetic](<https://support.keenetic.com/hero/kn-1013/en/21243-configuring-a-wireguard-vpn-between-two-routers.html?utm_source=chatgpt.com>).

## 4. План реализации

Я бы разбил проект на пять этапов.

1. Этап 1. Базовый VPN через VPS
   - Установить WireGuard на VPS.
   - Создать отдельные ключи для каждого Keenetic.
   - Подключить оба роутера как клиентов.
   - Настроить маршрутизацию между LAN.
   - Проверить доступность устройств в обе стороны.
   Критерий готовности: LAN-to-LAN работает через VPS
2. Этап 2. Автоматизация управления
   Написать Control Plane:
   - Регистрация Keenetic.
   - Идентификаторы устройств.
   - Выдача конфигураций WireGuard.
   - Обновление конфигураций.
   - Контроль состояния соединений.
   - Отзыв доступа и ротация ключей.
   Рекомендую Go для API и управляющего агента.
3. Этап 3. Исследование NAT
   На обоих роутерах определить:
   - WAN IP.
   - Внешний IP по STUN.
   - Тип NAT и особенности UDP-фильтрации.
   - Стабильность отображения UDP-портов.
   - Доступность IPv6.
   Важно: STUN не всегда позволяет достоверно классифицировать NAT. Окончательное решение принимается по результатам ICE connectivity checks.
4. Этап 4. P2P и ICE
   - Реализовать signaling.
   - Организовать сбор и обмен ICE-кандидатами.
   - Проверять пары UDP-адресов.
   - Выбирать успешный маршрут.
   - Сохранять VPS relay как резерв.
   - Контролировать потерю связи и повторное соединение.
   Здесь потребуется отдельный транспортный адаптер для VPN-пакетов.
5. Этап 5. Автоматическое переключение
   - Приоритет прямого P2P.
   - Переход на relay при потере прямого соединения.
   - Возврат на P2P после восстановления.
   - Мониторинг RTT, потерь и пропускной способности.
   - Проверка отсутствия циклов маршрутизации.

## 6\. Важный вопрос реализации на Keenetic

Я бы не начинал с установки собственного ICE-агента на роутеры.

Сначала стоит выяснить, позволяет ли конкретная модель Keenetic и её версия KeeneticOS использовать нужные сетевые компоненты. Для MVP штатного WireGuard-клиента достаточно.

Для полноценного P2P потребуется решить, как ICE и WireGuard будут использовать один и тот же транспортный путь. Простое изменение внешнего endpoint WireGuard после ICE-проверки не гарантирует сохранение того же NAT mapping.

Поэтому возможны две реализации:

- Вариант 1: ICE управляет внешним UDP-транспортом, внутри которого работает VPN.
- Вариант 2: отдельный userspace VPN-транспорт с интегрированным ICE, а WireGuard остаётся базой для криптографии либо заменяется подходящим туннельным механизмом.

Второй этап разработки лучше выбирать после проверки возможностей конкретного Keenetic.

## 7\. Что нужно выяснить перед разработкой

Есть три параметра, которые существенно влияют на выбор реализации.

1. Модели Keenetic. Например, Hopper, Giga, Ultra и версии KeeneticOS. От этого зависит возможность запуска дополнительных компонентов.
2. Требования к пропускной способности. Например, 50, 100, 300 или 500 Мбит/с.
3. Количество роутеров. Только две точки или в будущем планируется полноценная сеть из множества Keenetic?

Мой предварительный выбор:

Рекомендуемая архитектураWireGuard Hub → Control Plane → ICE P2P → VPS Relay fallback.

При этом я бы сохранил возможность работы через обычный WireGuard Hub даже при полном отказе ICE-компонентов.

Это даст надёжный VPN в первой версии и позволит постепенно превратить его в автоматическую P2P-систему без публичных IP на роутерах.

Какие именно модели Keenetic будут участвовать в проекте? Это наиболее важная информация для выбора реализации клиента.
